API reference ​

Everything exported by ThermophysicalDB.jl, grouped by purpose. The functions of the last section are not exported and are subject to change; they are documented for contributors.

Getting the database ​

ThermophysicalDB.ThermophysicalDB Module
julia
ThermophysicalDB

Download, cache and query experimental thermophysical property data from public databases, starting with the NIST/TRC ThermoML Archive.

source
ThermophysicalDB.database Function
julia
database(; update = :notify, reload = false, rebuild = false, dir = thermoml_dir(),
         user_databases = true) -> Database

The ThermoML database, ready to query with points.

The first call ever downloads the archive from NIST, parses it and saves a binary cache next to it, which takes a few minutes. Later sessions only check whether NIST has a newer archive (update as in ensure_archive: :notify warns, :install upgrades, :never stays offline) and then load the cache, which is much faster than parsing. A changed archive or schema version rebuilds the cache automatically.

The databases of your own that were saved with save_database are opened too (from databases, by default the folder databases next to dir; their tables are read only when a query needs them). user_databases = false gives the archive alone.

prefetch_compounds = n also asks PubChem, once the database is ready, for the n most measured compounds that the compound database lacks (see prefetch_compounds!; it needs the network and downloads the compound database if it is not there yet). It is off by default, and a failure only warns.

Calling database() again in the same session returns the same object immediately; reload = true repeats the update check and the load, rebuild = true also ignores the cache and parses the archive again.

julia
db = database()
points(db; component = "hexane", property = "Thermal conductivity")

ThermophysicalDB.check_update Function
julia
check_update(; dir = thermoml_dir()) -> UpdateStatus

Compare the local archive with the latest one published by NIST. Never throws because of network problems: when NIST cannot be reached the built-in release list is used and source is :builtin. When NIST answers but its record holds no archive link we recognise, source is :unrecognized and a warning is logged, once per session.

An archive republished under the same name counts as an update: when the version is the installed one but the .sha256 published by NIST differs from the digest recorded at installation, the state is :update_available and republished is true.

ThermophysicalDB.ensure_archive Function
julia
ensure_archive(; update = :notify, dir = thermoml_dir()) -> Manifest

Make sure a verified ThermoML archive is available locally and return its manifest (see archive_path for the file). If nothing is installed, the latest archive is downloaded. Otherwise update decides what happens when NIST has a newer one:

  • :notify (default): keep using the local archive and log a warning;

  • :install: download and switch to the newer archive;

  • :never: do not even contact NIST.

ThermophysicalDB.install_archive! Function
julia
install_archive!(path; version = nothing, sha256 = nothing, dir = thermoml_dir(),
                 keep_old = false) -> Manifest

Install a ThermoML archive that is already on disk, e.g. one downloaded in a browser from https://data.nist.gov/od/id/mds2-2422. The file is verified against its SHA-256 (taken from sha256, else from path * ".sha256", else from the releases this package knows), copied into the data directory and recorded, exactly like a download. Afterwards database uses it.

version ("2020-09-30") is read from a file name such as ThermoML.v2020-09-30.tgz when not given. A file whose digest does not match is rejected and nothing is installed.

Selecting and extracting points ​

ThermophysicalDB.points Function
julia
points(dataset_or_view; kwargs...) -> DataView

Select experimental points. Every keyword is optional and they combine with AND; calling it on a DataView refines that view, so filters can be chained.

  • component: a name, formula or InChIKey, or a vector of them. Names are matched loosely (case, accents, hyphens and spaces are ignored, so "iso-butane" finds "isobutane"; see find_compounds); a compound id or the result of find_compounds is accepted too. With match = :any (default) a system qualifies if it contains any of them, with match = :all if it contains all of them. exact = true requires the system to consist of exactly the listed components (component = "methane", exact = true is pure methane).

  • pure: true for single-component systems, false for mixtures.

  • property: a label such as "Mass density" (any case), a Regex, or a vector.

  • temperature, pressure: (low, high); nothing leaves a side open. Plain numbers are in K and kPa; Unitful quantities are converted, e.g. temperature = (20u"°C", 40u"°C") and pressure = (1u"atm", 2u"atm"). Points without that condition are excluded when the filter is given.

  • doi, author (substring, any case), source (e.g. "thermoml"), year.

A component or property that matches nothing throws an ArgumentError, so a typo is never mistaken for "no data".

Given a LinkedDatabase (see link_compounds) instead of the dataset, a component can also be a synonym, a CAS number, a PubChem CID, an InChI or a SMILES, and an ambiguous text is resolved by asking the user (keyword choose).

source
julia
points(db::Database; kwargs...) -> DatabaseView

Select points in every database that can have them, with the keywords of points over a dataset, and duplicate: false (the default) leaves out the points that another database with a higher priority holds too, and the points that were entered twice in a database of yours (the later copy is left out; it stays in the database); true keeps every point, and a DuplicateRules leaves them out with the tolerances you choose (see duplicates for what a repeated point is, and conflicts for the points that disagree, which are never left out). A component or property that no database knows is an ArgumentError; one that some databases lack is not. A component given as the result of find_compounds(db, text) is translated to the identifiers of each database.

ThermophysicalDB.mixture Function
julia
mixture(dataset_or_view, components...; exact = true, kwargs...) -> DataView

Points of the systems made of the given components, in any order: mixture(db, "nitrogen", "isobutane") is the binary nitrogen + isobutane. It is points(db; component = [components...], match = :all, exact = true, kwargs...), so components are matched loosely (see find_compounds) and every other keyword of points (property, temperature, ...) can be added. With exact = false systems that contain further components are included.

When nothing is found, a message tells whether the components do occur together with others, so an empty result can be told apart from a too strict one.

ThermophysicalDB.find_compounds Function
julia
find_compounds(dataset, text; limit = 10) -> CompoundMatches

Find the compounds that text refers to, however it is spelled. Case, accents, hyphens and spaces are ignored ("Iso-Butane" is "isobutane"), "n-hexane" also finds "hexane", and a short list of abbreviations and alternative spellings is understood ("IPA", "sulphur", "propylene"). An InChIKey or a formula ("N2") is matched as written; a formula can be shared by several compounds ("C4H10" is butane and isobutane).

The result lists exact matches first (:exact), then names that contain the text or are contained in it (:contains, so "butane" also lists "isobutane"), then names a few spelling errors away (:similar). points tells how many measurements are in systems that contain each compound, which shows at a glance which spelling is the one with data.

Pass the result as component to points to select every compound it lists, or pick rows with component = result.id[2].

julia
find_compounds(db, "iso-butane")
points(db; component = find_compounds(db, "isobutane"; limit = 1))

julia
find_compounds(dataset, db, text; limit = 10) -> CompoundMatches

find_compounds that also understands what the compound database knows: a CAS number, a PubChem CID, an InChI, a SMILES ("SMILES=...") or any synonym of a compound leads to the ThermoML compounds with the same InChIKey. find_compounds(db, cdb, "oxidane")          # from a synonym that no article used

ThermophysicalDB.table Function
julia
table(view; units = :native, policy = :nominal, quantities = nothing) -> NamedTuple

Materialise a DataView as a NamedTuple of columns (a valid Tables.jl table, so DataFrame(table(v)) works). One row per point, with the columns

source, doi, year, components, xkind, property, method, phase, temperature, pressure, x1, x2, x3, value, unit, unc, unc_k, unc_level, unc_k2.

With details = true the table also has what the source says about the data: purpose (purpose of the experiment), unc_method (how the uncertainty was evaluated), digits, temperature_digits and pressure_digits (significant digits, -1 when not given) and, for each component i, purityi, purity_kindi and purity_basisi from its sample (see sample_table); NaN or "" where the source does not say.

units = :native keeps the unit of the source (kPa, kJ/mol, ...). units = :si converts value, unc, unc_k2 and pressure (to Pa) and reports the SI unit in unit. unc_k2 is the uncertainty at k = 2 (see coverage_factor for policy); it is NaN where it cannot be derived without inventing data, and a warning counts such rows. Compositions x1..x3 are as the source gave them: xkind tells what they express. With composition = :mass_fraction (or any other of COMPOSITION_SCALES) they are converted to that scale; solvent, molar_mass, compounds, density, fetch_molar_mass and strict are those of convert_composition, NaN marks a point that could not be converted (details = true adds composition_status with the reason, and a warning counts them).

With quantities = Unitful (or the module of another units package that has an extension, such as DynamicQuantities) the columns temperature, pressure, value, unc and unc_k2 hold quantities of that package (temperature in K, pressure in kPa or Pa for units = :si). A column of quantities has one concrete type, which keeps broadcasting fast, so the selection must contain a single unit: narrow it with property first, or an ArgumentError lists the units found. Dimensionless properties stay plain numbers. The unit column is kept as text.

unit asks for the columns value, unc and unc_k2 in another unit of the same quantity, for a selection with a single unit: as text (unit = "mW/m/K", "Btu/hr/ft/degF", "mbar"), which the package reads with exact rational arithmetic (SI prefixes, compound units and the customary units are understood), or as a unit object of a loaded units package (unit = u"mW/m/K"), which also makes the columns quantities of that package. The dimensions are checked, and units = :si cannot be given at the same time. A degree of temperature is an interval inside a compound unit; a temperature scale with an offset ("degC") is refused as the unit of a property.

When unit (or temperature_unit, pressure_unit) is an object of a units package, the package is asked for the unit as text. If the exact parser of this package reads it, the conversion is done here, exactly, and the package only receives the converted column; if it does not (a symbol that is not known here), the units package converts. temperature_unit and pressure_unit give the columns temperature and pressure in any unit of those quantities, as text ("degC", "degF", "mK", "bar", "mbar", "psi", "N/m2") or as a unit object; pressure_unit cannot be combined with units = :si.

ThermophysicalDB.sample_table Function
julia
sample_table(x; ids) -> NamedTuple

One row per sample of a Dataset, or of the samples behind the points of a DataView: a Tables.jl table with the columns

sample, doi, compound, inchikey, number, origin, status, supplier, nsteps, purity, purity_kind, purity_initial, purity_initial_kind, water, purity_basis, analysis, purification.

Purities and water are fractions, NaN where the source does not state them; purity_kind is "mass", "mole", "volume" or "unspecified" ("" without a purity) and purity_basis is "supplier", "measured" or "estimated" ("" when unknown). analysis and purification list the methods of every step, separated by "; ". Use purity_step_table for the steps one by one.

purity_step_table(x) -> NamedTuple

ThermophysicalDB.condition_table Function
julia
condition_table(x) -> NamedTuple

One row per condition of a Dataset, or of the experiments and points behind a DataView: everything the ThermoML source states besides the temperature, the pressure and the composition of the components (frequency, the composition of a solvent, a second density, ...), and the phases of the system. A Tables.jl table with the columns

role, doi, experiment, measurement, group, label, value, digits, phase, component, phase_component.

  • role is "constraint" (fixed for the whole experiment), "variable" (changes from point to point; measurement is the row of the point, the same row as in table's source) or "phase" (a phase of the system; label is its name).

  • group is the kind of condition in the ThermoML schema ("eMiscellaneous", "eSolventComposition", ...) and label its name with the unit, as the source wrote it.

  • digits are the significant digits of value (-1 when not given); value is NaN for a phase.

  • component is the compound the condition refers to and phase_component the one its phase is stated for ("" for none).

Composition scales ​

ThermophysicalDB.convert_composition Function
julia
convert_composition(values, from, to; molar_mass, solvent = 0, density = NaN) -> Vector{Float64}

Convert the amounts of the components of one mixture from the scale from to the scale to (see COMPOSITION_SCALES). values has one entry per component; the entry of the solvent (for the scales that are per amount of solvent) and of a component that is the rest of a set of fractions can be NaN. molar_mass gives the molar mass of each component in g/mol, solvent the position of the solvent in values, and density the density of the solution in kg/m3 (needed by :molarity and :mass_concentration only).

julia
convert_composition([0.1, NaN], :molality, :mole_fraction; molar_mass = [58.44, 18.015], solvent = 2)

Nothing is guessed: what the conversion needs and was not given is an ArgumentError that says what it is. To convert the points of a selection of the database, use the method that takes a DataView.

Physics. Mole and mass fractions, molality and the ratios do not depend on the temperature or the pressure; they differ only by the molar masses. The molarity is moles per volume of solution, so it depends on the density of the solution, which depends on the temperature, the pressure and the composition itself: the density of that state has to be given.

source
julia
convert_composition(view, to; solvent = nothing, molar_mass = nothing, compounds = nothing,
                    density = nothing, fetch_molar_mass = false, strict = false) -> CompositionConversion

Express the composition of every point of a DataView in the scale to (one of COMPOSITION_SCALES), whatever scale the sources used. The data of the archive are not changed. A point that cannot be converted gets NaN and a status that says why; with strict = true the first such point is an ArgumentError instead.

  • solvent: the component that is the solvent, by name, identifier (CAS number, InChIKey, ...) or identifier of the dataset; a list is accepted. It is needed when the source or the target scale is per amount of solvent (molality, ratios). It is never guessed.

  • molar_mass: a dictionary from names (or InChIKeys, or identifiers of the dataset) to molar masses in g/mol, e.g. Dict("water" => 18.01528). What you give wins over everything else.

  • compounds: the compound database (compound_database) or a LinkedDatabase, where the molar masses that you did not give are looked for (they include what was fetched from PubChem). With fetch_molar_mass = true a compound that the database does not know is asked from PubChem by its InChIKey; the network is not used otherwise.

  • density: the density of the solution in kg/m3, needed to convert from or to the molarity or the mass concentration: a number for every point or a vector with one value for each point. It is never estimated. A function of the state is not accepted yet.

Fractions that the source gave with all components must add up to one within COMPOSITION_SUM_TOLERANCE; a single missing fraction is the rest. See convert_composition for one mixture.

ThermophysicalDB.add_measurement! Function
julia
add_measurement!(experiment; property, unit = "", value, temperature = NaN, pressure = NaN,
                 composition = (), unc = NaN, unc_k = NaN, unc_level = NaN,
                 unc_temperature = NaN, unc_pressure = NaN, unc_composition = NaN,
                 group = "", method = "", phase = "") -> Int

Add one point to an experiment of a database of your own and return its row. property is the name ThermoML uses ("Mass density"), unit the unit of a plain value and unc ("kg/m3"): the point is the same property as the archive's only when the label and the stored unit are the same text. composition is the amount of each component in the scale of the experiment (as many as you know, in the order of components), unc is the uncertainty (with its coverage factor unc_k or its level of confidence unc_level, when you know them). What is not given is NaN; nothing is filled in.

temperature, pressure, value and unc are converted here, once, to the numbers the database stores. Each can be a plain number (temperature in K, pressure in kPa, value and unc in unit), a text with a unit ("20 degC", "0.01 bar", "0.9982 g/cm3", unc = "0.1 %") or a quantity of a units package that is loaded. The value is stored in the unit that the databases already use for the property (of the same dimension), and in the SI when none has it; a unit of another quantity, a gauge pressure or a unit that cannot be read is an ArgumentError. An uncertainty is a difference: only its scale is converted. With no unit, a plain number is stored as it is.

unc_temperature, unc_pressure and unc_composition (one for each amount, or a single value for all the amounts that are given) are the uncertainties of the conditions of the point; they are optional and stored in the uncertainty table (see uncertainty_table). A plain number is a standard uncertainty ( ) in K, kPa or the scale of the composition; a text with a unit is a difference ("0.05 degC" is 0.05 K, "0.09 degF" is 0.05 K); and UncertaintyTerm(0.1; k = 2) states the coverage. A percentage is taken of the value in an absolute scale: of the temperature in kelvin, even when the temperature was given in degC ("0.01 %" of 25 degC is 0.01 % of 298.15 K, that is 0.030 K) and, for degF, equally of the rankine scale (the same number of kelvin); of the pressure in kPa; and of the amount as stored. A relative uncertainty of a temperature in an offset scale would otherwise depend on where its zero is.

add_reference_data!(db; reference, experiments, database = nothing, compounds = nothing,

ThermophysicalDB.duplicates Function
julia
duplicates(view; rules = nothing) -> DuplicateReport
duplicates(db; rules = nothing, kwargs...) -> DuplicateReport

The points of a selection that two databases hold both, as pairs: the point of the database that wins and the other one. A selection made with points(db; duplicate = false) gives the report that left them out, with the points that are gone; kwargs are those of points.

Two points are the same when

  1. they come from the same work: the DOI is the same, or, when one reference has no DOI, the first author and the year are (and the titles agree when both have one). When nothing tells where a point comes from it is never taken for a repeated one, however close it is to another;

  2. they are of the same compounds and property, the temperatures are within rules.temperature (0.1 K) and the values within rules.value (0.1 %);

  3. the pressures are within rules.pressure (0.01 bar) and the amounts of the components within rules.composition. A pressure or an amount that one of the points does not have is not compared: if the temperature and the value agree, the points are the same. When the amounts are written in different scales they are not compared and both points are kept.

A point without temperature is never compared. The points of one experiment are never repeats of each other (a database may measure the same state twice), but the same work entered twice in a database of yours (the same file imported again) is: the points of the later experiment are the repeats. No database is changed. See DuplicateRules and conflicts.

ThermophysicalDB.LinkedDatabase Type
julia
LinkedDatabase

What link_compounds returns: the ThermoML dataset (dataset), the compound database (compounds), the table of links between them (links, a CompoundLinks) and the choices the user made when a name was ambiguous (choices).

julia
set_uncertainty!(ds; scope, row, quantity, statistical, device, combined, expanded,
                 k = 2.0, level = NaN, method = "", evaluation = "") -> NamedTuple

For a point, the combined and the expanded uncertainty are derived when not given, in this order of precedence:

  1. the combined term is used as given;

  2. otherwise the expanded term gives it,  ;

  3. otherwise   over the statistical and device terms of the point and of its experiment (uncorrelated terms, GUM 5.1.2).

Detecting outliers ​

ThermophysicalDB.find_outliers Function
julia
find_outliers(view_or_dataset; kwargs...) -> OutlierResult

Look for wrong points in a selection of the database. It works like points: hand it a DataView (or a whole Dataset) and it returns, in an OutlierResult, three views that partition the input: kept, outliers and disputed.

julia
v = points(db; component = "water", property = "Mass density")
kept, outliers, disputed = find_outliers(v)
reasons(result)        # why each excluded point was excluded

Three analyses run in order. Each needs enough neighbouring points to say something; a point without them is reported as not tested, never as validated.

  1. Physical rules (physical = true): conditions no real measurement can break (negative temperature, a fraction above 1, a non-positive density, cp/cv < 1, ...), plus the limits in known_limits. A point that fails is an outlier and is left out of the next analyses.

  2. Trend along one axis (trend = true): points of the same system, property and phase that share the other conditions are put in order along T, P or composition, and a window of window neighbours is fitted with a robust parabola. Points of different sources and methods are compared with each other. The distance of each point to the curve fitted without it, in units of the expected scatter, is its z.

  3. Joint surface (joint = true): when two or more axes vary, a quadratic surface with cross terms is fitted to the neighbors nearest points in all axes at once, which finds points that are consistent along each axis but not together.

The z values of each analysis are pooled and tested with Rosner's generalized extreme studentized deviate test ((Rosner, 1983)), which finds several outliers without one hiding another. A point flagged by the surface analysis alone is disputed; one flagged along an axis is an outlier. Several points of the same publication that all lie on one side of the others are disputed as a systematic offset of the source (source_offset = :outlier makes them outliers).

Keywords

  • physical, trend, joint: switch each analysis on or off.

  • window = 9: points per local parabola (at least 5). min_points = 7: shortest line that is analysed. neighbors = nothing: points per surface window, 4p with p = 6 (two varying axes) or 10 (three) coefficients.

  • consensus_fraction = 0.6: fraction of a window that must agree with the curve. inlier_threshold = 2.5: distance, in units of scatter, beyond which a point is not part of the curve; a point is also never flagged with |z| below it.

  • level = 0.05: probability of flagging anything in a set of points that has no outlier, shared among the tests that run on a subgroup. max_outliers = nothing: most outliers looked for per test, a count or a fraction (default 0.1 of the points). critical = :auto: critical values from Rosner's formula with a correction for small samples with several steps; :rosner is the plain formula. Both are closed formulas, nothing is simulated (see esd_critical_values).

  • transform = :auto: coordinates of the fit; :none, or a NamedTuple with response (:auto, :log, :identity), T (:auto, :inverse, :identity) and P (:auto, :log, :identity).

  • tolerance = (T = 0.1, P = 0.01, x = 1e-3): differences below which two states are the same (K, fraction of the pressure, composition).

  • policy = :nominal: how declared uncertainties are brought to a common basis, as in table.

  • known_limits = nothing: a Dict from property label to (low, high); either side may be nothing. Example: Dict("Mass density" => (0, 2500)).

  • source_offset = :disputed, sign_sigma = 2.0.

  • tile = 3: largest number of neighbouring points that share one surface fit in the joint analysis (1: every point is fitted on its own). screening = 0.7: in the joint analysis every tile is first fitted with a cheap robust fit; the tiles where a point lies beyond screening * inlier_threshold (and the ones around a point beyond inlier_threshold) are fitted again with the more expensive and more robust consensus fit. 0 repeats every tile, which is the slowest and most conservative setting.

  • seed = 1: seed of the deterministic generator that draws the subsets of the consensus fit. The same seed always gives the same result, on any number of threads.

  • max_joint_points = 250_000: largest subgroup given to the joint analysis.

Results do not depend on the number of threads. The estimates assume the points of one subgroup are independent; they are not independent when one publication reports a whole series, which is why a systematic offset gets its own category.

ThermophysicalDB.Transformation Type
julia
Transformation(log_response, inverse_T, log_P)

The coordinates in which a subgroup is fitted. Many properties are close to straight lines or gentle parabolas only after a change of variable, and a local parabola fitted in the wrong variable leaves systematic residuals that look like outliers:

  • log_response: fit ln y instead of y. Viscosity, vapor pressure, diffusion coefficients and the Henry constants span decades and follow Arrhenius-like laws.

  • inverse_T: use 1/T instead of T. It goes with log_response because ln y ≈ A + B/T for an activated process (B = -E/R for a viscosity).

  • log_P: use ln P instead of P. Automatically it is chosen only for the properties that follow a power law of the pressure in a gas (kinematic viscosity, thermal diffusivity, diffusion coefficient: y ∝ 1/P because they carry a factor 1/ρ), and only in a gas phase. Elsewhere it is not: a liquid density is close to linear in P (the Tait equation is linear in ln(P + B) with B of the order of hundreds of MPa), a gas density is linear in P at low pressure, and a viscosity follows Barus' law ln η ≈ a + αP. ThermophysicalDB.esd_critical_values Method
julia
esd_critical_values(n, r, level; method = :auto)

Critical values λ₁, …, λᵣ of the generalized ESD test for n values and at most r outliers, as a vector. They are computed in closed form, so they are exactly reproducible and cost O(r) evaluations of Student's t quantile.

  • method = :rosner: Rosner's formula, rosner_lambda, at the given level.

  • method = :auto (default): the same formula at the level level / (1 + 3 (r - 1) / n). The formula treats the steps as if each were a test of its own at level, while the procedure declares an outlier when ANY step exceeds its value; the correction pays for that. It does nothing for r = 1 (Grubbs' test is exact) and little for r ≪ n.

ThermophysicalDB.flag_certainty Method
julia
flag_certainty(z) -> Vector{Float64}

Estimated probability that each value of the pool z is a true outlier, 1 - fdr, where fdr is the tail-area false discovery rate of (Efron, 2007): among the k values at least as far from zero as |zᵢ|, about n · 2Φ(-|zᵢ| / σ₀) are expected from a pool without outliers, so the fraction of false discoveries is that over k (at most 1). σ₀ is the scale of the bulk of the pool, estimated from its median absolute value and never taken below 1: a pool whose standardized residuals are wider than they should be (noisier than the model assumes) gets a low confidence however large its extremes look. The estimate is empirical and approximate; it is a measure of how well separated the flags are from the rest, not a guarantee.

ThermophysicalDB.lqs_consensus! Method
julia
lqs_consensus!(ws, q, cutoff)

Least quantile of squares on the window ((Rousseeuw, 1984)): among the surfaces through p points of the window, the one for which the q-th smallest scaled residual |yᵢ - ŷᵢ| / uᵢ is smallest, so that at least q points lie within that distance of it. The subsets are drawn with the generator of ws.rng (deterministic), and the winner is refined by concentration steps: refit by weighted least squares on the q points closest to the current surface, which never makes the fit of those points worse. The mask is left in ws.mask: the points within cutoff times the scale of the winner (the scale is the larger of the quantile over cutoff and the declared uncertainty, as in lqs_parabola).

source
ThermophysicalDB.lqs_parabola Method
julia
lqs_parabola(t, y, u, q) -> Union{Tuple{Vector{Bool},Float64},Nothing}

Consensus of a window with a parabola y ≈ c₀ + c₁ t + c₂ t², by least quantile of squares (Rousseeuw 1984): among the parabolas through three points of the window, the one for which the q-th smallest weighted residual |yᵢ - ŷᵢ| / uᵢ is smallest, so that at least q points lie within that distance of it.

The three-point parabolas are enumerated exhaustively, not drawn at random: the result is deterministic and, unlike a count-based RANSAC with a fixed tolerance, does not need to know the scatter in advance. A window has at most a few tens of points, so C(m, 3) is small. Returns the points within cutoff * max(floor, sₚ / cutoff) of the winner, as a mask, and that scale; nothing when no three points have distinct t.

ThermophysicalDB.process_joint! Method
julia
process_joint!(task, set; threaded = true)

Fit the local quadratic surface of every point of the subgroup and fill the result arrays of task; the module header of surface.jl explains the strategy. In short: the points are grouped in tiles that share a window of neighbors points; all tiles get a cheap robust fit; the tiles with a point beyond screening * inlier_threshold (and the tiles around a point beyond inlier_threshold) are fitted again with the least-quantile-of-squares consensus. Distances are measured in the coordinates scaled to the unit range of the subgroup, so that a kelvin and a mole fraction weigh as much as their spans say.

The result does not depend on the number of threads: every tile writes only the entries of its own points, and the random numbers of a tile depend on its number only.

ThermophysicalDB.robust_refit Method
julia
robust_refit(X, y, u, consensus, known, cutoff) -> Union{WindowFit,Nothing}

refit_window iterated until the inlier set stops changing. The consensus step keeps the best q points, which is a truncated sample, so the scale estimated from it is too small and z would be inflated for every point of an honest data set. After each fit the inliers are recomputed as the points with |z| ≤ cutoff under the scale of that fit, which is corrected for the truncation at cutoff (see truncated_variance); the process settles at a scale that agrees with the data ((Rousseeuw and Leroy, 2003)). At most 12 steps are taken.

truncated_variance(c) -> Float64

Variance of a standard normal variable conditioned on |Z| ≤ c: 1 - 2c φ(c) / (2Φ(c) - 1).
