# CHANGELOG

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog],
and this project adheres to [Semantic Versioning].

## [Unreleased]

- Databases know when they were created and last edited (`created_at(db, name)`, `modified_at(db, name)`, shown by `db`); the stamps are in the file and in `member.toml`, and files written before they existed take the time of the file (no schema change)
- The spreadsheet template says the XLSX.jl and Julia versions and the UTC time that made it, and has the document properties (creator, date, versions) that Excel shows under File > Info
- Quality checks in the tests: Aqua and JET, both ordinary tests that pass with no known reports; fixed an ambiguity of `convert_native`, a call to `first` with an unsupported keyword when joining template files, and the places where a possible `nothing` was not handled
- Benchmarks with AirspeedVelocity.jl (`benchmark/`): a synthetic database of a chosen size, groups for loading, adding points, the filters one after another and in one call (also over a linked compound database), the units packages, the spreadsheet template and the outlier search; the workflow `Benchmark.yml` compares every pull request with the latest release and comments time and allocated memory, and `benchmark/memory_report.jl` reports what stays in memory after loading, table by table
- `points(db; ...)` leaves out the repeated points by default (`duplicate = false`; `duplicate = true` shows every point), also the points of an experiment that repeat an earlier experiment of the same database of yours (the same file imported again); they stay in the database, replicates inside one experiment are kept, and `add_reference_data!` warns about them
- `link_compounds(db, compound_database())` now works over a `Database` with several members: each member is linked, `points`, `mixture` and `find_compounds` on the result search all of them with any name, synonym, CAS number or CID of the compound database, and the table of links has the column `database`; `find_compounds(db, compounds, text)` is the same search over every database
- The menus of the spreadsheet template (method, phase, sample source, supplier, purity analysis, purification) are filled with the values that the databases already hold, most used first, followed by generic choices; `add_template_experiments!` keeps them
- Added `export_points`, which writes the points of a selection to a directory (created if needed), one file per format chosen with `formats`, a tuple of symbols: `:csv`, `:md`, `:tex`, `:json`, `:jld2`, `:xlsx` (added to the default when XLSX.jl is loaded) `:thermoml` (the JSON form of ThermoML) and `:thermoml_xml` (ThermoML XML); the references table and the `.bib` are written next to the table formats, and a path with a file extension is an error
- Added the condition table (schema version 5, the cache is rebuilt): the constraints (including those on temperature, pressure and composition, written back as `Constraint`), the phases and the variables of the archive that are not temperature, pressure or composition, the phases of properties and their reference states, the solvent of a property and the `TRCRefID` of an article are kept and written by the ThermoML formats; `condition_table` gives them as a table
- Added the uncertainty table (schema version 6, the cache is rebuilt): the statistical, device, combined and expanded uncertainty of the property, the temperature, the pressure and the composition of the data you supply, each with its coverage factor and level of confidence; `set_uncertainty!` stores the terms and derives the missing combined and expanded ones (GUM 5.1.2 and 6.2), `uncertainty_table` reads them, `expanded_uncertainty` gives error bars at any `k`, and the `.json` of `export_points` carries the separate terms (the ThermoML formats keep only the expanded uncertainty of the property)
- Units are now package extensions: Unitful, DynamicQuantities and FlexUnits (FlexUnits is experimental) are weak dependencies, and `table(v; quantities = Unitful)` (or `DynamicQuantities`, `FlexUnits`) returns columns with units; there is no other keyword: without `quantities` the columns are plain `Float64`, and the module of the package you pass (`Unitful`, `DynamicQuantities`, `FlexUnits`) chooses how the quantities come out. Limits of `points` and the units of `reference_summary` accept quantities of any loaded backend. The data stay `Float64` in the units of the archive; quantities exist only at the boundary
- Unit conversions are exact: every factor and offset is a rational (`Rational{Int128}`) derived from the legal definition of the unit (inch, pound, standard gravity, rankine, ...), the factors of the unit catalog are derived from the unit strings and checked for dimension, and a chain of conversions is composed in rationals and rounded to `Float64` once. Conversions of a column are a single pass (identity, scale, or scale and offset)
- `table(v; unit = ...)` gives the columns `value`, `unc` and `unc_k2` in any unit of the same quantity, for a selection with one unit. The unit is text, read with exact rational arithmetic (SI prefixes and compound units: `"mW/m/K"`, `"mbar"`, `"Btu/hr/ft/degF"`, with Btu, calorie, hr, min, L, gal, P, St, lb, lbf, ft, in, psi, ...), or a unit object of Unitful, DynamicQuantities or FlexUnits, which also returns quantities of that package; the dimensions are checked. A new function `unit_factor` completes the protocol of the extensions
- `table(v; temperature_unit = ..., pressure_unit = ...)` gives the columns `temperature` and `pressure` in any unit of those quantities, by name (`"degC"`, `"degF"`, `"mK"`, `"bar"`, `"mbar"`, `"psi"`, `"N/m2"`) or as a unit object; the conversion is exact, with the offset of degC and degF. When a unit object comes from a units package, its text is read by the exact parser of this package and, if it is understood, the whole conversion is done here and the package only receives the column; otherwise the package converts. The unit reader accepts spaces, `^`, parentheses and `·`, as the units packages print units (`"mW m^-1 K^-1"`, `"W/(m*K)"`). The extensions may add `unit_text` (optional)
- Every unit conversion goes through the exact arithmetic: also the quantities that the user gives (limits of `points`, values and uncertainties, `reference_summary`) are converted here, with the exact value of the number and one rounding, when the units package gives the unit as text that is understood; the package converts only a unit whose symbol is not known. The names of a temperature scale are aliases of one definition (`°C`, `degC`, `℃`; `°F`, `degF`, `℉`; `°R`, `degR`, `Ra`), and a property that is a temperature (in kelvin) can be asked in `degC` or `degF`, with the offset for the value and the scale only for the uncertainty. A quantity with a wrong dimension is an `ArgumentError` for every package of units. The extensions implement `quantity_parts` (optional) and `package_native_value`, `package_native_difference` and `package_convert_native` instead of the old `native_value`, `native_difference` and `convert_native`
- The terms of `set_uncertainty!` accept a quantity of any units package, a text with a number and a unit (`"0.5 mW/m/K"`, `"5 mbar"`), and a relative uncertainty (`"2 %"`, `"500 ppm"`, `2u"percent"`, a fraction of the value of the same quantity at the point); they are converted as differences into the unit of the database with the exact arithmetic of the package, and `UncertaintyTerm` keeps the value as given until it is stored. A quantity with a wrong dimension is an `ArgumentError` for every package
- Reduced the memory of the database by about 38 % (516 to 317 MB for 2.78 million measurements): `unc_k`, `unc_level` and the new `assessment` are stored as one byte per row pointing into their few distinct values (`PooledFloats`, same values on reading), the identifier columns of the measurements use the narrowest unsigned integer, the evaluator and the assessment number of the uncertainty moved from the extras table (5.5 million repeated rows) to columns of the measurements, the extras that are the same for every point of a measured property are stored once for the whole block (`:block` scope, `block` column) and still read for every point by `extra_numbers` and `extra_texts`, and a freshly built database releases the spare capacity of its columns. The cache schema version is now 8, so the cache is rebuilt once
- Added `convert_composition` and the keyword `composition` of `table` and `export_points`: the composition of a selection is expressed in one scale (mole fraction, mass fraction, molality, amount or mass ratio, moles per mass of solution, molarity or mass concentration) whatever scale each source used. The molar masses are the ones you give, then the compound database, and with `fetch_molar_mass = true` PubChem; the solvent and the density of the solution are given by you and never guessed, and a point that cannot be converted keeps `NaN` with the reason in `composition_status`. The data of the archive are not changed. `compound_links` accepts `only` to link some compounds.
- A database read from the cache file now reads its large tables only when something uses them (lazy loading, `LAZY_FIELDS`: samples, purity steps, extra fields, conditions and the text pool of the extras), so `database()` followed by `points`, `table` and the other queries of the core tables keeps about a quarter less in memory and reads the file about four times faster once compiled (0.47 s instead of about 2 s for 2.78 million measurements). `loaded_tables(ds)` says what is in memory, `validate` and the cache writer read what is missing, and a cache file that was replaced after the database was read is refused with a message to load it again. The cache format is unchanged.
- `database()` now returns a `Database`: independent databases (`members`) that look like one. The ThermoML archive is the member `thermoml`; points of the user (`:user`) and from the literature (`:literature`) are separate members with the same tables, each in its own file, with a priority (default archive, literature, user) for a repeated point. A registry of global numbers for compounds, properties and references, always in memory, maps the numbers of each member to the global ones and, from a small catalog of each file, tells which members a query can find something in: only those are read. `points(db; ...)` returns a `DatabaseView` with one `DataView` per database that has points (`parts`), `table` joins them (column `database`), `find_compounds(db, text)` joins the compounds, and a database with one member behaves as the dataset did. Export, outliers and the reference tables work on one database for now.
- Added the data entry spreadsheet (needs XLSX.jl): `export_template(db, path; experiments = n)` writes a workbook with a guide, the reference and its compounds and samples, and `n` pairs of experiment and points sheets, with menus filled from your databases, the units and uncertainty of each column and cells that turn red when they cannot be read; `import_template(db, path; check = true)` lists every mistake with its sheet and cell, and `import_template(db, path)` adds the data to a database of your own through `add_reference_data!` (a vector of paths joins files of the same work, for works with more than 25 compounds); `add_template_experiments!` adds pairs to a file that is already started.
- The data entry workbook is written by the package itself (the OOXML parts, with data validation, conditional formatting and protection), ZipArchives is a new weak dependency of the extension and `add_reference_data!` has a `dry_run` keyword. The uncertainties of the composition, temperature and pressure and the data of the samples are read but not stored yet, and are reported
- Added the tutorial "Adding your own data" (`docs/src/20-tutorials/80-own-data.md`): a hypothetical article and own measurements (volumetric heat capacity at constant pressure; all values invented) added step by step with `add_reference!`, `add_experiment!` and `add_measurement!`, then with the spreadsheet (`export_template`, `import_template(...; only_check = true)`), with two filled examples to download (`example-literature.xlsx`, `example-own-measurements.xlsx`); the documentation environment needs XLSX
- Added the uncertainties of the conditions of a point: the keywords `unc_temperature`, `unc_pressure` and `unc_composition` of `add_measurement!`, the columns `unc_temperature`, `unc_pressure` and `unc_x1`...`unc_x3` of `add_reference_data!` and the `u(x)`, `u(T)` and `u(P)` columns of the spreadsheet are stored in the uncertainty table (expanded term with its coverage factor and the derived combined standard uncertainty). A plain number is a standard uncertainty, `UncertaintyTerm` states the coverage, a text with a unit is a difference, and a percentage is always taken of the value in an absolute scale: the temperature in K (also when it was given in degC, and in degF, whose rankine fraction is the same) and the pressure in kPa; documented in the uncertainty manual
- Changed `import_template`: the keyword `check` is now `only_check`. `only_check = true` adds nothing, not even the database of the file, and the report has `imported`, `thermoml_compatible` and `thermoml_failures` (the criteria that keep the data from being written as valid ThermoML: citation, property name, phase, composition of a mixture, coverage of an uncertainty); the result of an import has them too. The tutorial "Adding your own data" ends with the tables of what the package and ThermoML require of a reference. The phase menu of the template now offers ThermoML phase names. A coverage text of the template no longer depends on the language of Excel (it showed 038 for 37.62 in a Portuguese Excel, and the coverage factor as "2,")
- Added the databases of the user: `add_database!` (an empty member, `:user` or `:literature`), `add_reference!`, `add_experiment!`, `add_measurement!` and `add_reference_data!` (everything an article measured, checked before anything is added), `save_database`, `set_priority!` and `databases_dir`. A compound must come with an InChIKey, a CAS number or a name the compound database knows exactly (`cas:<number>` as key while the InChIKey is unknown); the archive is never written; nothing is saved unless asked; `database()` opens the saved databases (`user_databases = false` for the archive alone)
- Added the search for repeated points between databases: `points(db; duplicate = false)` leaves out the points that a database with a higher priority holds too (`duplicate = DuplicateRules(...)` chooses the tolerances: 0.1 K, 0.01 bar, 0.1 % by default), `duplicates` and `conflicts` list the pairs (`DuplicateReport`, a table), and `add_reference_data!` warns when the same work is already in another database. A work is told by its DOI, or by first author and year (and title); with no information on the origin two points are never taken for the same; a pressure or an amount that one of them lacks is not compared; the same state of the same work with another value is a conflict and both points are kept
- Added the compound database (`compound_database`): the names, CAS number, PubChem CID, formula, molar mass, SMILES, InChI and InChIKey of about 76 000 compounds, with salts, hydrates and the ions of brines, kept apart from the ThermoML data. The lists are downloaded once from a fixed commit of the chemicals repository (MIT license), checked against their SHA-256 digests and cached, so the package works offline afterwards. `lookup_compounds` finds a compound by name, CAS number, CID, InChIKey, InChI, SMILES or formula; `link_compounds` matches the compounds of the archive with it (by InChIKey, InChI and, flagged as less reliable, by name, with a comparison of the formulas and of the InChIs) without changing the archive; `find_compounds(db, cdb, text)` searches the archive through the identifiers of the compound database; `register_compound!` and `save_compounds` keep the compounds and molar masses that the user adds, which survive a new version of the lists
- `link_compounds` returns a `LinkedDatabase`: the ThermoML archive together with the compound database and the table of links (`linked.links`). `points`, `mixture` and `find_compounds` accept it, so a compound can be named by any synonym, CAS number, PubChem CID, InChI or SMILES; when a text leads to more than one compound of the archive, a numbered menu asks which one (`choose = :ask`, `:error`, `:all` or a `Dict` of prepared answers; the answers are kept and `forget_choices!` clears them). The archive is never changed
- Added the search in PubChem on request: `fetch_pubchem!` and the keyword `online = true` of `lookup_compounds`, `points` and `mixture` ask PubChem (by name, CAS number, CID, InChIKey, InChI or SMILES) for a compound that the database does not know, with a numbered menu when a name belongs to several compounds. The answers are kept as one JSON file for each compound, laid over the list every time the database loads (precedence: lists, PubChem, your own compounds); questions it could not answer are remembered for 180 days; requests are spaced (3 per second by default, `pubchem_rate!`), and a service failure throws `PubChemError` and changes nothing. The network is never used without `online = true` or `fetch_pubchem!`; a text the database already knows exactly is not asked unless `force = true` (or `refresh = true`)
- Added `prefetch_compounds!`, which asks PubChem, by InChIKey, for the compounds among the `top` most measured of the archive that the compound database lacks (ionic liquids, for example; nothing is asked once they are known), and the keyword `prefetch_compounds = n` of `database()` to do it when the archive is ready (off by default; a failure only warns)
- The name search is faster for plain ASCII names (`normalize_name`), and `DownloadError` can carry its own advice
- Added NOTICE.md, legal notices in the README and in the documentation, and the data source references in CITATION.cff
- Added `find_outliers`, which splits a selection into kept points, outliers and disputed points with the reason for each (physical rules, local parabolas along each axis, a joint surface when several axes vary, and the generalized ESD test), plus `reasons`, `diagnostics` and `esd`; see the manual page "Detecting outliers"
- Test fixtures use fictitious bibliographic data
- Every export of ThermoML Archive data carries one notice (origin, full citation of the dataset version 1.2, modified and not endorsed by NIST/TRC, credit the articles, link to the terms): `.csv`, `.tex`, `.json`, `.jld2`, `.xlsx`, the `@comment` of a `.bib`, and the tables of `latex_table`, `markdown_table` and `csv_table` (`notice = false` leaves it out); the text lives in `src/notice.jl` and is also shown on the first download
- Added the manual page "Exporting data" and the tutorial "Tables for a paper", which exports the references table (Markdown and LaTeX), the points table and a complete `.bib`
- `export_points` no longer repeats in every row what the references table says or what is the same in the whole selection: the `method` and `phase` columns are not written by default, nor `components` for a single system or `property` for a single property; `details = true` writes them
- `export_points` warns when `references = false` and `reference = :key` leave a `.csv` or `.tex` without a way back to the DOIs
- The update check warns, once per session, when NIST answers but its record holds no recognisable archive link, tells this apart from being offline, compares the published `.sha256` with the installed one so that an archive republished under the same name counts as an update, and accepts small variations of the archive file name

- The `.bib` written by `bibtex`, `write_bibtex`, `write_references` and `export_points` ends the credits with the entry of this package, built from `CITATION.cff` (version, the DOI of the release and the `preferred-citation` article when the file has them) after a comment that asks to cite it; `include_package = false` leaves it out. No table mentions it. YAML.jl is a new dependency

- Citation keys follow the pattern of the reference manager, `surname` + `year` + first word of the title in lower case (`myers1999surfaces`, `sd` for a missing year, `anonymous` for a missing author), so a `.bib` agrees with a library that generates the same keys; a repeated key gets `a`, `b`, ...
- The references of the package live in `CITATION.cff` (`references:`, with an `abbreviation` and `keywords` each): the ThermoML Archive and standard of every `.bib`, the dataset in the notice and the bibliography of the documentation (`docs/src/refs.bib` is now generated by `docs/make.jl`) are all derived from it, and the file is read once, when the package is precompiled
- Added `ThermophysicalDB.check_references`, which verifies the file (required fields, keywords, keys equal to the pattern) and compares each article with the record of the DOI resolver
- The documentation has its own `docs/package.json`: the default of DocumenterVitepress plus `overrides` that raise `vite`, `esbuild`, `glob` and `minimatch` to patched versions, so that `npm audit` reports no vulnerability (the default reports 10, all in development tooling)
- The documentation credits the articles whose data its examples use: a folded block "Sources of the data" at the end of each page that shows data, and a page "Data credits" that lists all of them and offers the `.bib` for download; the front page lists the versions of Julia, the package, the archive and the packages of the examples, with a `versions.toml` for download. All of it is generated by the build (`docs/DocsCredits.jl`)
- The build of the documentation does not contact the DOI resolver by default (it uses the cache of the data directory and the metadata of the archive); `THERMOPHYSICALDB_DOCS_ONLINE=true` asks for the missing entries
- The build of the documentation logs the time of every phase and page and ends with a table of where the time went (`docs/DocsTiming.jl`; `THERMOPHYSICALDB_DOCS_TIMING=false` turns it off)
- Added the PrecompileTools workload file `src/precompile.jl`, ready to receive workloads; it never calls `database` or anything that downloads

- Schema version 2: the database now keeps what each article says about its samples, and an older cache is rebuilt on the next use. New `SampleTable` (one row per described sample: origin, status, final and initial purity with its basis, water content, analysis and purification methods, and `purity_basis`, the class `supplier`, `measured` or `estimated` derived from the analysis methods) and `PurityStepTable` (every purification step with the purities, water and halide contents, significant digits and free-text methods); each experiment points to the samples of its components and records its purpose; each measurement records the significant digits of the value, the temperature and the pressure, the coverage factor and the method of evaluating its uncertainty. The abstract of the article is kept as an extra field. A sample that an article does not describe is treated as any other absent value
- Added `sample_table` and `purity_step_table`, which give the samples of a dataset or of a selection as Tables.jl tables, and `table(view; details = true)`, which adds the purity of each component, the digits, the purpose and the uncertainty method to the points
- `reference_summary` and its LaTeX, Markdown and CSV tables have the columns `purity`, `purity_min`, `purity_max`, `purity_basis`, `purity_method`, `purification`, `sample_source` and `supplier`; the default tables show the purity, its analysis and the purification when an article states them, and `columns` chooses any of them
